# 环境搭建清单

> **版本**：v1.1
> **日期**：2026-09-30（v1.1 补入 `docker-compose.yml` 全文与四个组件的逐步安装命令）
> **适用**：电信用户行为分析系统（P1）5 人开发小组
> **目标**：**5 台 VM 环境完全一致** —— 不一致则出问题时无法互相对齐、无法互相复现
> **用法**：逐项执行，做完把 `☐` 改成 `☑`；**每完成一个阶段先验证，再往下走**

## 阶段 0 · 宿主侧（Windows）——每人一次

> 在 VMware 里改配置**必须先关机**，因此这几项一起做完再开机。

| # | 项目 | 目标值 | 操作位置 | ☐ |
|---|---|---|---|---|
| 0.1 | 内存 | **6 GB** | VMware →「编辑虚拟机设置 → 内存」 | ☐ |
| 0.2 | CPU | **4 核** | 「编辑虚拟机设置 → 处理器 → 核心总数 4」 | ☐ |
| 0.3 | 磁盘 | **60 GB** | 「编辑虚拟机设置 → 硬盘 → 扩展」 | ☐ |
| 0.4 | 网络模式 | **NAT（VMnet8）**，不要改桥接 | 「编辑虚拟机设置 → 网络适配器」 | ☐ |

## 阶段 1 · 系统侧（VM 内）——每人一次

### 1.1 磁盘扩容（⚠️ 两段，缺一不可）

| # | 步骤 | 命令 | 期望结果 | ☐ |
|---|---|---|---|---|
| 1.1.1 | 记录扩容前状态 | `df -hT /` | 容量 18G、可用约 16G | ☐ |
| 1.1.2 | 安装 growpart | `yum install -y cloud-utils-growpart` | 装好 `cloud-utils-growpart-0.29-5.el7` | ☐ |
| 1.1.3 | 扩**分区** | `LC_ALL=C growpart /dev/sda 2` | `CHANGED: partition=2 ... new: size=...` | ☐ |
| 1.1.4 | 扩**物理卷** | `pvresize /dev/sda2` | PSize 由 19.51g → 59.51g | ☐ |
| 1.1.5 | 扩**逻辑卷** | `lvextend -l +100%FREE /dev/centos/root` | root 由 17.47g → 57.51g | ☐ |
| 1.1.6 | 扩**文件系统** | `xfs_growfs /` | `data blocks changed from ... to ...` | ☐ |
| 1.1.7 | 验证 | `df -hT /` | 容量 **58G**、可用 **56G** | ☐ |

**⚠️ 坑 1：不要用 `parted` 做这件事。**
CentOS 7 自带的是 parted **3.1 版，没有 `resizepart` 子命令**（3.2 才加入）。网上大量教程给的
`parted -s /dev/sda resizepart 2 100%` 在这里会直接失败——**更坏的是它打印一段帮助信息后以退出码 0 退出**，
被 `&& echo "OK"` 一类的写法误判成成功，让人以为扩了其实根本没扩。**必须用 `growpart`。**

**⚠️ 坑 2：`growpart` 必须强制英文 locale。**
直接敲 `growpart /dev/sda 2` 会报
`unexpected output in sfdisk --version [sfdisk，来自 util-linux 2.23.2]`——
growpart 靠正则解析 `sfdisk --version` 的**英文**输出，中文 locale 下直接解析失败。
**必须写成 `LC_ALL=C growpart /dev/sda 2`。**

**🚫 全程不需要重启，也不需要 umount。**
XFS 支持在线扩容，1.1.4–1.1.6 都在挂载状态下执行。任何让你先 `umount /` 的教程都是错的（而且根目录也卸不掉）。

**🚫 不要动 swap。** 本次扩容全程没碰 2 GB 的 swap，它是正常的。

| # | 项目 | 命令 | 期望结果 | ☐ |
|---|---|---|---|---|
| 1.2.1 | 时区 | `timedatectl` | `Time zone: Asia/Shanghai (CST, +0800)` | ☐ |
| 1.2.2 | 当前时间 | `date` | 与宿主 Windows 一致 | ☐ |

## 阶段 2 · 目录规划——5 人必须完全一致

| # | 项目 | 约定值 | ☐ |
|---|---|---|---|
| 2.1 | 项目根目录 | `/opt/demo01` | ☐ |
| 2.2 | 建目录 | `mkdir -p /opt/demo01` | ☐ |
| 2.3 | 数据目录策略 | **一律用 Docker 命名卷（named volume）**，不 bind mount | ☐ |

> **2.3 是一条硬规矩，理由见下。**

```
/opt/demo01/
├── docker-compose.yml          ← 编排总入口
├── docker/                     ← 各组件的配置与初始化脚本
│   ├── mysql/  (init.sql, my.cnf)
│   ├── kafka/
│   ├── nginx/  (前端静态资源 + 反向代理)
│   └── sftp/   (上传目录挂载点)
├── business/                   ← Spring Boot（JDK 17）
├── realtime/                   ← Spring Boot（JDK 17）
├── offline/                    ← Spark 作业，独立 jar（JDK 11）
├── frontend/                   ← Vue3 + Vite
├── mock/                       ← 造数 / 埋点模拟脚本
└── docs/                       ← claude.md、开发文档.md、本清单
```

> 本条即 `开发文档.md` §10「硬性约束」的可执行版本，不是新决策。

**🚫 不要用 bind mount 挂数据目录（如 `./data/mysql:/var/lib/mysql`）。**
容器里的进程（mysql 用户 uid 999 等）和宿主 CentOS 的用户 uid 对不上，启动时会直接
`Permission denied`，而且报错信息很难指向真正的原因。**代码目录 bind mount 没问题**（只读挂载、uid 不影响），
**数据目录一律用命名卷**，让 Docker 自己管权限。

## 阶段 3 · 逐个起组件、逐个验证

> **核心原则：起一个 → 验一个 → 再起下一个。**
> 不要一次性 `docker compose up -d` 然后把四个组件一起排查——
> 四个同时不工作时，你无法判断是哪一个的问题，也不知道是谁把谁拖垮的。

**每个组件必须同时确认两件事**：
1. **能连通**（对应小节的验证命令）；
2. **重启能自愈** —— `docker compose restart <服务>` 后仍然正常，否则说明数据没落到命名卷上。
   第 2 条现在花 1 分钟，将来能省半天。

### 3.0 要装的软件清单

| # | 软件 | 首选 tag | 备选 tag | 宿主端口 | 用途 |
|---|---|---|---|---|---|
| 1 | MySQL | `mysql:8.4` | `mysql:8.0` | 3306 | 业务表 7 张 + 行为数据表 4 张，共库不同区 |
| 2 | Redis | `redis:7.4-alpine` | `redis:7-alpine` | 6379 | 缓存 / 在线用户数 / 实时指标 |
| 3 | Kafka | `apache/kafka:4.0.0` | `apache/kafka:3.9.1` | 不开放（理由见 3.6） | 行为日志 topic `behavior-log` |
| 4 | SFTP | `atmoz/sftp` | —— | **2222** → 容器 22 | 日志文件上传通道 |

**为什么这么选版本**：

- **MySQL 8.4**：2026 年 7 月起 MySQL 改用日历版本号，原来那条 8 线停在 8.4（上一个 LTS）。**8.0 已于 2026-04-21 进入 Sustaining Support**（只修致命故障，不再有常规补丁）。8.4 更新，8.0 对老内核更友好，故 8.4 优先、8.0 兜底。
- **Redis 用 `-alpine`**：alpine 用的是另一套 C 库（musl），**完全绕开 glibc 那套内核版本要求**。本机内核 3.10 非常老，这个后缀在这里是实打实的保险。
- **绝不写成 `mysql:8` / `redis:7`**：这俩是「跟着上游跑」的浮动名字，5 个人在不同时间 `docker pull` 会拿到不同版本，直接违背本清单开头的「5 台 VM 环境完全一致」。

### 3.2 拉镜像，实测锁定 tag（⚠️ 本阶段的关键一步）

镜像 tag **不凭印象写**：本机 Docker Hub 直连不通，只能走 `/etc/docker/daemon.json` 里配的镜像站，而镜像站的 tag 缓存可能滞后或缺档。逐个拉，拉不动就换备选。

```bash
docker pull mysql:8.4
docker pull redis:7.4-alpine
docker pull apache/kafka:4.0.0
docker pull atmoz/sftp
```

**怎么读结果**：

| 输出 | 含义 | 处理 |
|---|---|---|
| `Status: Downloaded newer image for ...` | 成功 | 记下这个 tag |
| `manifest unknown` / `not found` | 镜像站没缓存这个版本 | 换「备选 tag」再试 |
| `i/o timeout` / `TLS handshake timeout` | 网络问题 | 换镜像站单拉，见下 |

```bash
# 临时改用某一个镜像站单拉
docker pull docker.1ms.run/library/mysql:8.4
# 拉回来后打上正式名字，后续命令才认得
docker tag docker.1ms.run/library/mysql:8.4 mysql:8.4
```

**拉完记账**（`docker system df` 的输出留着，见附 A 坑 8）：

| # | 命令 | 用途 | ☐ |
|---|---|---|---|
| 3.2.1 | `docker images` | 四个镜像是否都在 | ☐ |
| 3.2.2 | `docker system df` | 记录实际占用，判断 vfs 下磁盘够不够 | ☐ |

> `apache/kafka:4.0.0` 若拉不到：先试 `docker pull apache/kafka:latest`，成了再用
> `docker inspect apache/kafka:latest --format '{{index .Config.Labels "org.opencontainers.image.version"}}'`
> 看它实际是几，回填到 compose 里。
>
> `atmoz/sftp` **不加 tag**（即 `:latest`）——该镜像 2021 年后就没更新过，老基座在本机内核上反而是优点。

### 3.3 编写 `docker-compose.yml`

```bash
mkdir -p /opt/demo01
cd /opt/demo01
vi docker-compose.yml
```

把下面整份粘进去，**用 3.2 实际拉成功的 tag 替换 `image:` 那几行**：

```yaml
# 电信用户行为分析系统 (P1) —— 基础设施编排
# 范围：MySQL / Redis / Kafka / SFTP 四件
#       HDFS 与应用三件套（business / realtime / frontend）见阶段 3.9 / 3.10
# 硬性约束：数据目录一律命名卷，禁止 bind mount（阶段 2.3）
# 凭证为演示用弱口令，非生产环境
#
# ⚠️ 四个服务统一 TZ=Asia/Shanghai。容器默认是 UTC，与宿主差 8 小时，
#    会让 event_time「判未来」和 24 小时时段热力图分桶全错，而且不报错。

services:

  mysql:
    image: mysql:8.4
    container_name: demo01-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: demo01_root
      MYSQL_DATABASE: demo01
      TZ: Asia/Shanghai
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
      - --default-time-zone=+08:00
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 40s
    networks: [demo01-net]

  redis:
    image: redis:7.4-alpine
    container_name: demo01-redis
    restart: unless-stopped
    environment:
      TZ: Asia/Shanghai
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks: [demo01-net]

  kafka:
    image: apache/kafka:4.0.0
    container_name: demo01-kafka
    restart: unless-stopped
    environment:
      TZ: Asia/Shanghai
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
      KAFKA_LOG_DIRS: /var/lib/kafka/data
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"
      KAFKA_HEAP_OPTS: "-Xmx512m -Xms256m"
    volumes:
      - kafka_data:/var/lib/kafka/data
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 >/dev/null 2>&1 || exit 1"]
      interval: 15s
      timeout: 10s
      retries: 10
      start_period: 30s
    networks: [demo01-net]

  sftp:
    image: atmoz/sftp
    container_name: demo01-sftp
    restart: unless-stopped
    environment:
      TZ: Asia/Shanghai
    # 格式：用户名:密码:uid:gid:目录名
    command: ["demo01:demo01_sftp:1001:1001:upload"]
    ports:
      - "2222:22"
    volumes:
      - sftp_data:/home/demo01/upload
    networks: [demo01-net]

networks:
  demo01-net:
    name: demo01-net
    driver: bridge

volumes:
  mysql_data:
    name: demo01_mysql_data
  redis_data:
    name: demo01_redis_data
  kafka_data:
    name: demo01_kafka_data
  sftp_data:
    name: demo01_sftp_data
```

**下面几处不是随手写的，改之前先看**：

| 写法 | 为什么必须这样 |
|---|---|
| 四个服务都有 `TZ` | 容器默认 UTC。阶段 1.2 只改了宿主机时区，容器**不继承** |
| MySQL 三个 `--character-*` / `--default-time-zone` | 8.4 默认已是 utf8mb4，但显式写死才能保证 5 台一致，也正是 3.4 要验的 |
| MySQL 用 `$$MYSQL_ROOT_PASSWORD` | Compose 里 `$$` 转义成一个 `$`，交给容器内的 shell 展开。写单个 `$` 会被 Compose 先吃掉 |
| Kafka 三个 replication factor = 1 | KRaft 单节点的经典启动失败点：默认是 3，单 broker 起不来 |
| Kafka **不配 EXTERNAL listener、不开放端口** | 一旦写宿主 IP，5 台 VM 的 IP 不同，文件就不再是同一份。当前没有任何东西需要从宿主连 Kafka（3.6 的验证在容器里做）。将来造数脚本要连时再加，做法见下方「将来让宿主直连 Kafka」 |
| Redis `--appendonly yes` | 不开 AOF，重启后 key 全丢，会把「命名卷没生效」误判出来 |
| 全部命名卷、零 bind mount | 阶段 2.3 的硬规矩 |
| 没写 `version:` | Compose v2 已废弃该字段，写了会打 warning |

**将来让宿主直连 Kafka**（现在不用做）：给 `kafka` 服务加一组 EXTERNAL listener——`environment` 里改三行、`ports` 里加一行。**广播地址写 `localhost` 而不是 IP**，这样 5 台 VM 的文件仍然一模一样：

```yaml
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093,EXTERNAL://:9094
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,EXTERNAL://localhost:9094
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,EXTERNAL:PLAINTEXT
    ports:
      - "9094:9094"
```

> 只开放 9092 而不配 EXTERNAL 是**更坏的做法**：宿主连得上，但拿回的元数据里写的是 `kafka:9092`，宿主解析不了这个名字，表现为「端口通、就是收发不了」。

校验语法（**能提前抓出缩进错、字段名错**）：

```bash
docker compose config
```

无报错、无 warning 才算过。

docker exec -it demo01-mysql mysql -uroot -pdemo01_root -e "SELECT 1;"   # ☐

### 3.6 Kafka（KRaft，四件里最容易卡的一个）

```bash
docker compose up -d kafka
docker compose logs -f kafka      # 看到 "Kafka Server started" 后 Ctrl+C
docker compose ps                  # STATUS 应为 healthy
```

建 topic：

```bash
docker exec -it demo01-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic behavior-log \
  --partitions 1 --replication-factor 1
```

确认 topic 名，**不要直接看 `--list`**（那会连内部 topic 一起列出来）：

```bash
docker exec -it demo01-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list | grep behavior-log
```

一发一收，**开两个终端**：

```bash
# 终端 A —— 先挂上消费者
docker exec -it demo01-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic behavior-log --from-beginning

# 终端 B —— 发一条
echo '{"event_code":"view_home","user_id":null}' | \
  docker exec -i demo01-kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic behavior-log
```

终端 A 收到那条 JSON 即通过。

```bash
# 自愈验证
docker compose restart kafka
docker exec -it demo01-kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list | grep behavior-log    # ☐ topic 仍在
```

**起不来时先看日志里这几行**：报副本因子 → 三个 `REPLICATION_FACTOR` 没设成 1；报 controller → `KAFKA_CONTROLLER_QUORUM_VOTERS` 里的主机名与 `KAFKA_PROCESS_ROLES` 对不上；报内存 → 调小 `KAFKA_HEAP_OPTS`。

### 3.7 SFTP

```bash
docker compose up -d sftp
docker compose ps
```

**从宿主传一个文件上去**（`put` 的源文件在宿主，不在 VM；下例假定你在宿主 Windows 的 Git Bash 里操作）：

```bash
echo "hello demo01" > /tmp/sftp_test.txt

sftp -P 2222 demo01@127.0.0.1
```

进了 `sftp>` 提示符后：

```
put /tmp/sftp_test.txt
ls
bye
```

`ls` 能看到 `sftp_test.txt` 即通过。首次连接会问 `Are you sure you want to continue connecting?`，输 `yes`。宿主若无 sftp 客户端：`yum install -y openssh-clients`。

```bash
# 自愈验证：restart 后重新 sftp 上去 ls，文件仍在    ☐
docker compose restart sftp
```

> SFTP **没配健康检查**——该镜像里没有可靠的健康探测手段，所以 `docker compose ps` 里它不显示 `healthy`。**这不是故障**，按上面的 sftp 客户端方式验即可。

## 附 A · 已知坑清单（汇总）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | parted 3.1 无 `resizepart` | 打印帮助后**退出码 0**，被误判为成功 | 用 `cloud-utils-growpart` 的 `growpart` |
| 2 | growpart 在中文 locale 下失败 | `unexpected output in sfdisk --version` | `LC_ALL=C growpart /dev/sda 2` |
| 3 | 以为扩了磁盘其实没扩 | VMware 改了 60 GB，`df -h` 还是 18G | 阶段 1.1 四层都要走：分区→物理卷→逻辑卷→文件系统 |
| 4 | 数据目录用 bind mount | 容器启动即 `Permission denied` | 数据用命名卷，代码可 bind mount |
| 5 | 四个容器一起起 | 全部不工作，无法定位 | 起一个验一个 |
| 6 | VM 时间不对 | 图表有数据但全错，不报错 | 阶段 1.2 先校时区 |
| 7 | 镜像在新内核上构建 | 旧内核 3.10 拉不起来 | 每个镜像首次拉起单独确认（阶段 3.2） |
| 8 | **Docker 落回 `vfs` 存储驱动** | `docker info` 显示 `Storage Driver: vfs`；镜像层成倍占盘，磁盘莫名被吃光 | 根因是根 XFS 的 `ftype=0`（CentOS 7.2 的 `mkfs.xfs` 默认值），overlay2 在 XFS 上要求 `ftype=1`。**该属性建文件系统时写死，改不了，只能重格**；阶段 1.1 的扩容在原有 LV 上做，没有重格。**先不修**——跑完阶段 3.2 用 `docker system df` 量实际占用，56G 放得下就接受（修它要重装系统，对「5 台一致」的代价远大于收益） |
| 9 | **Docker Hub 直连不通** | `docker pull` 报 `i/o timeout` / `TLS handshake timeout` | 实测 `registry-1.docker.io` 与 `auth.docker.io` 均超时（HTTP 000），只有 `/etc/docker/daemon.json` 里的镜像站可达。**拉取必须走镜像站**，而镜像站的 tag 缓存可能滞后或缺档——这正是阶段 3.2 要逐个实拉的原因。单拉某个镜像站见 3.2 |
| 10 | **容器时区不继承宿主** | 阶段 1.2 校过时区，容器内仍是 UTC，`SELECT NOW();` 与宿主差 8 小时 | 每个服务显式写 `TZ: Asia/Shanghai`（阶段 3.3）。漏了会让 `event_time` 判未来、时段热力图分桶全错，**且不报错**，与坑 6 是同一类隐蔽故障 |
