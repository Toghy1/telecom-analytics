# 环境搭建清单

> **版本**：v1.0
> **日期**：2026-09-30
> **适用**：电信用户行为分析系统（P1）5 人开发小组
> **目标**：**5 台 VM 环境完全一致** —— 不一致则出问题时无法互相对齐、无法互相复现
> **用法**：逐项执行，做完把 `☐` 改成 `☑`；**每完成一个阶段先验证，再往下走**

---

## 使用说明

- 本清单**只管流程与验证**。具体的镜像版本、端口号、卷名以 `docker-compose.yml` 为准（该文件尚未编写，见附 C）。
- **⚠️ 标记的，都是已经实测会卡住的地方，不要跳过。**
- **🚫 标记的，都是「不要做」的事**，通常是因为网上教程有误导。
- 全文命令均以 `root` 身份执行；VM 内 `#` 开头的行是注释，不用敲。

## 阶段 0 · 宿主侧（Windows）——每人一次

> 在 VMware 里改配置**必须先关机**，因此这几项一起做完再开机。

| # | 项目 | 目标值 | 操作位置 | ☐ |
|---|---|---|---|---|
| 0.1 | 内存 | **6 GB** | VMware →「编辑虚拟机设置 → 内存」 | ☐ |
| 0.2 | CPU | **4 核** | 「编辑虚拟机设置 → 处理器 → 核心总数 4」 | ☐ |
| 0.3 | 磁盘 | **60 GB** | 「编辑虚拟机设置 → 硬盘 → 扩展」 | ☐ |
| 0.4 | 网络模式 | **NAT（VMnet8）**，不要改桥接 | 「编辑虚拟机设置 → 网络适配器」 | ☐ |
| 0.5 | **拍摄快照** | 命名为 `base-env` | 「虚拟机 → 快照 → 拍摄快照」 | ☐ |

> **为什么 0.5 是必做项**：磁盘扩容、Docker 装歪、compose 起不来——任何一步搞砸，回滚快照 30 秒，重装系统 2 小时。这是全套清单里性价比最高的一步。
>
> **0.3 只是第一步。** 扩展出来的 60 GB 此时**系统根本看不见**，必须在阶段 1.1 里再走一遍「分区 → 物理卷 → 逻辑卷 → 文件系统」四层。只做 0.3 不做 1.1，等于没扩。

## 阶段 1 · 系统侧（VM 内）——每人一次

### 1.1 磁盘扩容（⚠️ 两段，缺一不可）

| # | 步骤 | 命令 | 期望结果 | ☐ |
|---|---|---|---|---|
| 1.1.1 | 记录扩容前状态 | `df -hT /` | 容量 18G、可用约 16G | ☐ |
| 1.1.2 | 安装 growpart | `yum install -y cloud-utils-growpart` | 装好 `cloud-utils-growpart-0.29-5.el7` | ☐ |
| 1.1.3 | 扩**分区** | `LC_ALL=C growpart /dev/sda 2` | `CHANGED: partition=2 ... new: size=...` | ☐ |
| 1.1.4 | 扩**物理卷** | `pvresize /dev/sda2` | PSize 由 19.51g → 59.51g | ☐ |
| 1.1.5 | 扩**逻辑卷** | `lvextend -l +100%FREE /dev/centos/root` | root 由 17.47g → 57.51g | ☐ |
| 1.1.6 | 扩**文件系统** | `xfs_growfs /` | `data blocks changed from ... to ...` | ☐ |
| 1.1.7 | 验证 | `df -hT /` | 容量 **58G**、可用 **56G** | ☐ |

**⚠️ 坑 1：不要用 `parted` 做这件事。**
CentOS 7 自带的是 parted **3.1 版，没有 `resizepart` 子命令**（3.2 才加入）。网上大量教程给的
`parted -s /dev/sda resizepart 2 100%` 在这里会直接失败——**更坏的是它打印一段帮助信息后以退出码 0 退出**，
被 `&& echo "OK"` 一类的写法误判成成功，让人以为扩了其实根本没扩。**必须用 `growpart`。**

**⚠️ 坑 2：`growpart` 必须强制英文 locale。**
直接敲 `growpart /dev/sda 2` 会报
`unexpected output in sfdisk --version [sfdisk，来自 util-linux 2.23.2]`——
growpart 靠正则解析 `sfdisk --version` 的**英文**输出，中文 locale 下直接解析失败。
**必须写成 `LC_ALL=C growpart /dev/sda 2`。**

**🚫 全程不需要重启，也不需要 umount。**
XFS 支持在线扩容，1.1.4–1.1.6 都在挂载状态下执行。任何让你先 `umount /` 的教程都是错的（而且根目录也卸不掉）。

**🚫 不要动 swap。** 本次扩容全程没碰 2 GB 的 swap，它是正常的。

### 1.2 时区与时钟

| # | 项目 | 命令 | 期望结果 | ☐ |
|---|---|---|---|---|
| 1.2.1 | 时区 | `timedatectl` | `Time zone: Asia/Shanghai (CST, +0800)` | ☐ |
| 1.2.2 | 当前时间 | `date` | 与宿主 Windows 一致 | ☐ |

> **为什么要在乎这个**：行为日志里的 `event_time` 要判「是否落在未来」（脏数据规则之一），
> 大屏的「24 小时时段热力图」也按这个时间分桶。**VM 时间偏 8 小时，这两块功能全错，而且错得很隐蔽**——
> 图表有数据、也不报错，就是不对。

### 1.3 容器运行时

| # | 项目 | 命令 | 期望结果 | ☐ |
|---|---|---|---|---|
| 1.3.1 | Docker 版本 | `docker version` | Server **26.1.4** | ☐ |
| 1.3.2 | Compose 版本 | `docker compose version` | **v2.27.1**（注意是 `docker compose`，不是老的 `docker-compose`） | ☐ |
| 1.3.3 | 开机自启 | `systemctl is-enabled docker` | `enabled` | ☐ |
| 1.3.4 | 冒烟测试 | `docker run --rm hello-world` | 打印 `Hello from Docker!` | ☐ |

### 1.4 基础信息登记（5 人对齐用）

| # | 项目 | 命令 | 记录 | ☐ |
|---|---|---|---|---|
| 1.4.1 | 内核 | `uname -r` | `3.10.0-327.el7.x86_64` | ☐ |
| 1.4.2 | 发行版 | `cat /etc/redhat-release` | CentOS Linux release 7 | ☐ |
| 1.4.3 | yum 源可用 | `yum repolist` | 能列出 base / extras / updates | ☐ |
| 1.4.4 | 本机 IP | `ip addr show` | 填入附 B 登记表 | ☐ |

> **内核版本要记下来的原因**：CentOS 7 的内核是 **3.10**，而 2024 年 6 月之后很多官方镜像
> 是按新内核构建的。**每个镜像第一次拉起时都要确认它能正常启动**，起不来的就换 tag——
> 这一步不做，等到写业务代码时才发现，就变成了「环境坑」而不是「代码坑」，排查成本翻倍。

## 阶段 2 · 目录规划——5 人必须完全一致

| # | 项目 | 约定值 | ☐ |
|---|---|---|---|
| 2.1 | 项目根目录 | `/opt/demo01` | ☐ |
| 2.2 | 建目录 | `mkdir -p /opt/demo01` | ☐ |
| 2.3 | 数据目录策略 | **一律用 Docker 命名卷（named volume）**，不 bind mount | ☐ |

> **2.3 是一条硬规矩，理由见下。**

```
/opt/demo01/
├── docker-compose.yml          ← 编排总入口
├── docker/                     ← 各组件的配置与初始化脚本
│   ├── mysql/  (init.sql, my.cnf)
│   ├── kafka/
│   ├── nginx/  (前端静态资源 + 反向代理)
│   └── sftp/   (上传目录挂载点)
├── business/                   ← Spring Boot（JDK 17）
├── realtime/                   ← Spring Boot（JDK 17）
├── offline/                    ← Spark 作业，独立 jar（JDK 11）
├── frontend/                   ← Vue3 + Vite
├── mock/                       ← 造数 / 埋点模拟脚本
└── docs/                       ← claude.md、开发文档.md、本清单
```

> 本条即 `开发文档.md` §10「硬性约束」的可执行版本，不是新决策。

**🚫 不要用 bind mount 挂数据目录（如 `./data/mysql:/var/lib/mysql`）。**
容器里的进程（mysql 用户 uid 999 等）和宿主 CentOS 的用户 uid 对不上，启动时会直接
`Permission denied`，而且报错信息很难指向真正的原因。**代码目录 bind mount 没问题**（只读挂载、uid 不影响），
**数据目录一律用命名卷**，让 Docker 自己管权限。

## 阶段 3 · 逐个起组件、逐个验证

> **核心原则：起一个 → 验一个 → 再起下一个。**
> 不要一次性 `docker compose up -d` 然后把五个组件一起排查——
> 五个同时不工作时，你无法判断是哪一个的问题，也不知道是谁把谁拖垮的。

> **本节待补**：镜像 tag、端口号、卷名以 `docker-compose.yml` 为准，该文件尚未编写。
> 下表中「验证什么」和「怎么验」是确定的，「用什么镜像」等 compose 写完后回填。

| # | 组件 | 验证什么 | 验证方式 | ☐ |
|---|---|---|---|---|
| 3.1 | **MySQL** | 能连上；字符集为 utf8mb4（否则中文姓名、套餐名称变问号） | 进容器执行 `mysql -uroot -p` → `SELECT VERSION();` → `SHOW VARIABLES LIKE 'character%';` | ☐ |
| 3.2 | **Redis** | 能写入、能读出、能设过期时间 | `redis-cli set k v` → `redis-cli get k` → `redis-cli ttl` | ☐ |
| 3.3 | **Kafka（KRaft）** | 能建 topic；能生产一条；能消费到那一条 | 用镜像自带的命令行工具建 topic + 一发一收 | ☐ |
| 3.4 | **SFTP** | 能从宿主传一个文件上去；文件出现在约定目录 | `sftp -P <端口> <用户>@<IP>` → `put` → `ls` | ☐ |
| 3.5 | **HDFS**（排最后，唯一可裁剪项） | NameNode 能起来、能建目录、能上传 | `hdfs dfs -mkdir` / `-put` / `-ls` | ☐ |
| 3.6 | **应用三件套** | business / realtime 能启、前端页面能打开 | 浏览器访问前端地址；调用一次 health 接口 | ☐ |

**每个组件必须同时确认两件事**：
1. **能连通**（上面的验证方式）；
2. **重启能自愈** —— `docker compose restart <服务>` 后仍然正常，否则说明数据没落到命名卷上。
   第 2 条现在花 1 分钟，将来能省半天。

## 附 A · 已知坑清单（汇总）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | parted 3.1 无 `resizepart` | 打印帮助后**退出码 0**，被误判为成功 | 用 `cloud-utils-growpart` 的 `growpart` |

| 3 | 以为扩了磁盘其实没扩 | VMware 改了 60 GB，`df -h` 还是 18G | 阶段 1.1 四层都要走：分区→物理卷→逻辑卷→文件系统 |

| 5 | 五个容器一起起 | 全部不工作，无法定位 | 起一个验一个 |
| 6 | VM 时间不对 | 图表有数据但全错，不报错 | 阶段 1.2 先校时区 |
| 7 | 镜像在新内核上构建 | 旧内核 3.10 拉不起来 | 每个镜像首次拉起单独确认 |
