## 1. 项目概述

| 项 | 内容 |
| --- | --- |
| 项目 | P1 电信用户行为分析系统（任务书标注为主线项目） |
| 业务外壳 | 电信自助营业厅（Web 端） |
| 最终交付物 | **可视化界面**——主页实时大屏 + 子页系统运行分析 |
| 验收侧重 | 「采集 → 清洗 → 入库 → 可视化」这条流水线搭得完不完整、能否跑通 |
| 部署环境 | Linux Docker；**开发环境同为 Linux 虚拟机**（VMware + CentOS 7），一套 compose 复用 |
| 数据来源 | 全部为模拟数据，不需要真实数据集 |
| 项目体量 | **不扩量**，按现方案实施并预留缓冲 |

**优先级**：可视化 > 数据链路 > 业务功能。业务系统保持轻量，开发时间向大屏倾斜。

**合规落点**（P1 思政要求）：用户信息与通信数据属敏感个人信息，落地「最小必要」（分析员不可见个人明细）与「脱敏」（管理员可见用户信息但手机号、身份证脱敏）。

## 2. 系统架构

### 2.1 Lambda 架构三层

| 层 | 组成 | 产出 |
| --- | --- | --- |
| **批处理层** | SFTP + HDFS + Spark | 全量历史数据 → **准确**的离线指标 |
| **速度层** | Kafka + 实时消费服务 | 增量数据 → **实时**指标 |
| **服务层** | MySQL + Redis → Vue3 + ECharts | 大屏与看板 |

### 2.2 两条链路全景

```
造数脚本 ──日志文件──> SFTP ──拉取──> HDFS ──> Spark 作业 ──┐
   │ 读 t_account 真实用户                                   │
   │ 注入 8% 脏数据                                          ▼
   │                                              MySQL：明细表(T-1 及以前)
   └──脏数据──> 埋点接口 ──> Kafka ──> 实时消费服务           + 离线指标表
                    ▲                    │        │
                    │                    ▼        ▼
              Playwright           Redis：实时指标  死信表
              (真实浏览器)              │
                                        ▼
                                   SSE 推送
                                        │
                                        ▼
                              Vue3 大屏（主页 · 用户行为分析）
```

### 2.3 指标分工原则（硬约束）

**大屏上每一项指标，只能由实时链路或离线链路其中之一产出，严禁两条链路各算一遍。**

| 链路 | 负责的指标 | 判定依据 |
| --- | --- | --- |
| 实时链路（Kafka） | 在线数、实时 PV/UV、实时趋势曲线、页面热度、行为类型分布、时段热力图 | 可增量累加 |
| 离线链路（Spark） | 行为漏斗转化、留存率、地域 / 套餐 / 活跃度分布 | 必须全量重算 |

**理由**：两条链路计算口径必然存在偏差，同一指标双路计算会导致数字对不上，是答辩时最易被追问的破绽。**大屏上每一块图表都必须能回答「这块数据来自哪条链路」。**

## 3. 工程结构

划分为**两个应用 + 三个支撑模块**：

| 模块 | 形态 | 职责 |
| --- | --- | --- |
| `business` | Spring Boot 应用 | 营业厅接口 + 管理后台接口 + **埋点上报接口** |
| `realtime` | Spring Boot 应用 | Kafka 消费、洗净判脏、实时指标、SSE 推送、死信写入 |
| `offline` | **独立 jar**（JDK 11） | Spark 批处理作业 |
| `frontend` | Vue3 工程 | 营业厅 + 分析平台（主页 / 子页） |
| `mock` | 脚本 | 批量造数（含脏数据注入）+ Playwright 实时流量 |

> ⚠️ **`offline` 必须独立成 jar，不得并入 Spring Boot 应用。** Spark 依赖树与 Spring Boot 大面积冲突（Scala 版本、Jackson 版本、日志实现），硬塞会陷入依赖地狱。

**运行时版本随之一并分层**：`business` / `realtime` 用 **JDK 17**，`offline` 用 **JDK 11**（Hadoop 3.x 官方支持 Java 8 / 11，JDK 17 上 HDFS 读写易撞模块访问权限错误）。同理，**`offline` 不得继承 `spring-boot-starter-parent`**——否则依赖管理被 Spring Boot BOM 覆盖，绕回依赖地狱。做法：`offline` 自成独立工程，或置于聚合 POM 下但显式不继承 Spring Boot parent。

**为什么业务系统与数据处理服务要分开**：Kafka 消费者是常驻长任务，Web 接口是请求-响应；同进程内消费线程与 Tomcat 线程池互相影响，且**重启业务系统会连带中断实时消费**。

## 4. 技术栈

### 4.1 技术要点（对齐 P1 评分清单）

与 P1 技术要点逐项对齐，**10 项一项不减**：

| # | 组件 | 采用方式 |
| --- | --- | --- |
| 1 | Kafka 实时接入 | **KRaft 模式，不引入 ZooKeeper** |
| 2 | SFTP 文件传输 | `atmoz/sftp` 轻量容器 |
| 3 | HDFS | 单机（NameNode + DataNode），副本数 1 |
| 4 | Spark 离线批处理 | 单机 `local[*]` 模式，不建集群；仅需 1—2 个作业 |
| 5 | Git | 项目管理 |
| 6 | 单点登录 | **JWT + Redis**，不搭 CAS / OAuth2 |
| 7 | SpringBoot 分层架构 | Controller → Service → Mapper |
| 8 | Redis | 缓存 + 在线用户数统计 + 实时指标 |
| 9 | VUE3 + ECharts | 实时大屏 |
| 10 | Docker 一键部署 | 一套 compose 同时用于开发与部署 |

**明确不采用**：Grafana（面板是配置而非开发）、Flink（调试成本是时间黑洞）、Filebeat / Logstash（采集方式为埋点直发 Kafka）。

**HDFS 排在开发序列最后，是唯一可裁剪项。** 若时间不足而裁剪，答辩口径为：「数据量在 GB 级，单机 HDFS 运维成本高于收益，Spark 直接读本地文件更合适」。

### 4.2 业务功能实现层选型

4.1 的 10 项是「大件」，决定系统由哪些组件构成；本节 7 项是**写业务功能时每天都要用的实现层选型**。两者是上下游关系，不冲突。

| # | 面向 | 选型 | 关键约束（写代码时必须守住） |
| --- | --- | --- | --- |
| ① | 运行时与构建 | 业务侧 **JDK 17 + Spring Boot 3.x**；离线侧 **JDK 11 + Spark 3.x** | `offline` **不得继承 `spring-boot-starter-parent`**；`jakarta.*` 取代 `javax.*`，决定全部依赖坐标 |
| ② | 数据访问层 | **MyBatis-Plus** | 配 `id-type: auto`（默认雪花 ID 与 `AUTO_INCREMENT` 冲突）；`t_account.status` **不用** `@TableLogic`；显式注册分页插件；SB3 下引 `mybatis-plus-spring-boot3-starter` |
| ③ | 认证授权 | **自研拦截器 + JWT + Redis** | 放行清单须一次定死：登录 / 游客浏览页 / **埋点上报接口** / SSE 端点 / Swagger 静态资源。漏放行表现为「全站 401」 |
| ④ | 接口文档 | **SpringDoc OpenAPI** | SB3 下坐标为 `springdoc-openapi-starter-webmvc-ui`；`/swagger-ui/**`、`/v3/api-docs/**` 须放行 |
| ⑤ | 前端 | **JavaScript + Element Plus** | 请求集中封装于 `src/api/`；axios 响应拦截器统一解包；**JSON 字段名沿用 `snake_case`，不做 camelCase 转换**；组件库按需引入，**大屏不引组件库**；**须配 `zh-cn` 语言包**——Element Plus 默认 locale 是英文，且按需引入不会连带引入语言包，不配的话分页控件显示 `Total 7`、表格空态显示 `No Data`、日期选择器弹出 `January`（**必须用 `el-config-provider`，不能用 `app.use(ElementPlus, { locale })`——后者会把整个库全量引入，破坏按需引入**） |
| ⑥ | 对象转换 | **手写**（不引 MapStruct） | **脱敏写在这里**（见下） |
| ⑦ | 通用配置 | Lombok / `LocalDateTime` / 埋点分类上报 / `@Cacheable` | 页面浏览类事件走**路由守卫自动上报**，交互动作类**手动调用** |

**配套约定**：统一响应体 `Result<T>`、`@RestControllerAdvice` 全局异常处理、`jakarta.validation` 参数校验。前端 SSE 客户端采用 `@microsoft/fetch-event-source`（原生 `EventSource` 不支持自定义请求头，token 送不出去）。

**统一响应体 `Result<T>`**（2026-09-30 定稿）：全部接口返回同一外壳，**只有 `data` 随接口变化**。

```json
// 成功
{ "code": 200, "message": "操作成功", "data": { } }
// 分页：分页信息放在 data 内部
{ "code": 200, "message": "操作成功", "data": { "total": 12, "pages": 2, "current": 1, "records": [] } }
// 业务失败
{ "code": 1001, "message": "账户余额不足", "data": null }
```

**失败分两层**——判据是「谁该处理」：

| 层 | 管什么 | 取值 | 谁来处理 |
| --- | --- | --- | --- |
| **HTTP 状态码** | 程序层面 | 401 未登录 / 403 无权限 / 500 服务端异常 | axios 拦截器，**写一遍覆盖全部接口** |
| **`code`** | 业务层面 | 200 成功；**1001 起**为业务错误码（不与 HTTP 状态码抢号） | 各页面按需处理 |

登录过期是**二十个接口共同的事**，写一次拦截器全覆盖；「余额不足」是**下单接口独有的事**，写在下单那个页面里。若全塞进 `code`，每个接口都要判一次是不是 401。

**分页口径**（2026-09-30 定稿）：分页类接口**入参**统一为 `page`（从 1 起）+ `size`；**返回**沿用上表 `data` 内的 `{ total, pages, current, records }`，与 MyBatis-Plus 的 `Page<T>` 字段**逐一对应**（后端用的就是它，见选型 ②，字段名无需转换）。营业厅各列表页默认 `size = 5`。

> 前端本阶段用假分页（`src/api/mock/paginate.js`），其返回值**刻意与 `Page<T>` 同形**——接线时只换函数体，页面组件一行不改。假数据形状若与真后端不一致，接线时页面要跟着改，与「把替换成本压到最低」的初衷正好相反。
>
> 入参与返回字段一律沿用全项目命名约定（`snake_case`），**不另创造 `offset` / `limit` / `pageNum` 之类的写法**。

**余量计算落在后端**（2026-09-30 定稿）：余量接口直接返回 `quota` / `used` / `remain` 三个数，**前端不做 `额度 − 已用` 的减法**。理由是这个减法牵着一个**不报错的坑**——`t_package.data_quota` 与 `t_usage.used_data` 单位若不一致（一侧 GB、一侧 MB），相减不抛异常、不报错，**结果只是错**，页面上显示成一个看起来完全正常的数字；而余量在「账户总览」与「余量查询」两处都要用，每多一处自己减一次，这个坑就多一个入口。

**脱敏的实现位置与格式**——由选型 ⑥ 直接推导，是本项目最容易踩的坑：

> 脱敏写在后端 Entity → VO 的手写转换里，**绝不在前端做**。

若后端返回完整手机号、由前端加星号显示，属**假脱敏**：F12 查看接口响应即可见完整号码，Postman 直调接口更是完全绕过，与 P1「最小必要」原则（数据根本不得到达那一层，而非「给了但我不看」）正好相反。正确形态是：接口返回的 JSON 中该字段本身即脱敏态，前端不含任何脱敏代码。

**脱敏格式**（2026-09-30 定稿）：

| 字段 | 格式 | 示例 | 依据 |
| --- | --- | --- | --- |
| `login_name`（手机号） | 前 3 后 4 | `138****1234` | 行业通行，无歧义 |
| `id_card`（身份证） | **前 6 后 4** | `310101********1234` | 18 位结构为 `6 位地区码 + 8 位出生日期 + 3 位顺序码 + 1 位校验码`；**前 6 后 4 恰好整段盖住最敏感的出生日期**，一位不多一位不少，同时保留可认读性 |

> 入库存**明文**，脱敏只发生在出参。用户查看本人信息同样脱敏（见 §6.4 #7）。

**大屏实现约定**（2026-09-30 定稿，适用于 §7 的两个页面）：

| 项 | 约定 | 理由（一句话） |
| --- | --- | --- |
| **适配方式** | 固定逻辑尺寸 **1920×1080** + CSS `transform: scale(k)` 整体缩放，`k = min(视口宽 / 1920, 视口高 / 1080)` | 大屏是固定尺寸的展示场景，宽度已知且固定；scale 是单一全局几何变换，元素**不需要感知缩放** |
| **图表 resize** | `EChart.vue` **刻意不监听 `window.resize`** | 逻辑尺寸恒定 ⇒ 容器 CSS 尺寸永不变；唯一的 resize 监听在 `ScreenLayout.vue`（重算 `k`） |
| **组件库** | 分析平台**零 Element Plus 依赖**——含子页的分页表格、来源筛选、分页器全部自绘 | 深色自绘视觉体系里插一套 `el-table`，要么风格突兀，要么写一堆 `:deep()` 覆盖；**覆盖组件库样式的代码量通常不比自己画一遍少** |
| **埋点** | 大屏两条路由**刻意不设 `meta.track`**，访问大屏不产生行为事件 | 分析平台是**观察者**，采集对象是「用户对系统做了什么」（§5.1），给它上报等于让系统观察自己 |
| **轴来源** | 横轴 / 分类轴**由常量清单或日历推导，不得由数据行推导**；缺值落 `null` 或零值，**不改变轴的长度** | 按数据行推轴时，缺值的那一档会被**静默抽掉**而非留空档，图上完全看不出少了 |
| **地图** | geoJSON 必须先 `registerMap()` 完成，**才允许** `setOption`；就绪前 option 为 `null` | ECharts 6 中未注册地图时 `geoSourceManager.load()` 返回 `undefined`，`MapSeries` 直接抛错，**不是画空白图** |
| **路由权限** | 两条大屏路由带 `requiresAuth` + `roles: ['ANALYST', 'ADMIN']`；`/user/*` 带 `roles: ['USER']`；「谁能进哪」由 `router/access.js` 的 `isRoleAllowed()` **统一判断**（守卫 / 登录页 `redirect` 校验 / 页头入口显示三处共用）；登录页按角色分流（`ANALYST` → 大屏，`USER` → 营业厅，`ADMIN` 暂落 `/`）；营业厅页脚的临时入口已删除；大屏头部已补**半透明 hover 退出链** | 2026-09-30 定稿并**当日落码**（原为待确认问题 26）。退出链是加 `requiresAuth` 的**前置条件**——否则 ANALYST 进得去出不来。`/user/*` 不含 `ADMIN`：那是用户自助页，数据源是当前电信用户，管理员进去看到的是**别人**的余额账单。规则只在路由表 `meta.roles` 写一份，三处调用共用 |
| **埋点角色闸** | 分析员与管理员**不产生任何行为事件**——闸落在 `utils/tracker.js` 的 `send()` **唯一出口**，而非各调用点 | 上报入口有三处（路由守卫的页面浏览、`login`、`logout`，将来还有 `order_package` / `submit_ticket`），逐个加判断迟早漏一个。角色表已定两者「不产生行为数据」；`login` 恰是漏斗**第二段**，漏报会让转化率莫名偏高却查不出来 |

> ⚠️ **`null` 绝不 `|| 0` 兜底**：留存 0% 是「一个人都没回来」，`null` 是「还算不出来」，是两句完全不同的话。大屏上刻意留可见缺口（09-30 的 `d1`、近 7 天的 `d7`），断线本身就是事实的可视化。
>
> ⚠️ **ECharts 实为 6.x**（`^6.1.0`），非此前文档所写的 5——版本号**以实查 `package.json` 为准**，理由与「选型① 中小版本在编写 POM 时实查后锁定」相同。
>
> ⚠️ **geoJSON 走 `public/map/china.json` 由浏览器按需 fetch**（582 KB，ECharts 6 仍不内置地图数据），**永不进入 JS bundle**；加载失败**必须 `console.error` 留声**——失败表现为「地域分布一直空着」，与「后端没返数据」长得一模一样。

> 选型的完整理由与权衡过程见 `claude.md` 决策「业务功能实现技术选型 ①—⑦」「统一响应体采用 `Result<T>`」「身份证脱敏格式定稿（前 6 后 4）」「大屏适配采用 `transform: scale()` 整体缩放」「分析平台不引 Element Plus，表格与控件全部自绘」「分析平台不产生埋点，且入口暂挂营业厅页脚」「离线指标横轴来自常量清单或日历，不来自数据行」「大屏地图必须先注册完成再绘制」「ECharts 版本由 5 修正为 6」「分析平台角色守卫与登录分流（问题 26 归档，改为现在就做）」（含其落码期修正 4 条）。

- 字段名一律 `snake_case`——与 MySQL 表、Spark 输出一致，落地时零转换。
- 事件编码采用 `动词_对象` 的 snake_case。
- Java 实体用 camelCase + `@JsonProperty` 映射回 `snake_case`。

- **`user_id` 可空，但游客事件照样入库**——游客事件是漏斗第一段，不可丢，靠 `session_id` 标识。

> ⚠️ **三个量纲的单位**（2026-09-30 定稿）：`data_quota` = **GB**、`voice_quota` = **分钟**、`sms_quota` = **条**。`t_usage` 与前端展示**一律沿用同一套**。
> 单位必须全链路统一，因为余量由 `t_package.data_quota − t_usage.used_data` 相减得出——两侧单位若不一致（一侧 GB、一侧 MB），**相减不报错、不抛异常，只是结果错**，页面会显示成一个看起来完全正常的数字。这类错误不崩不炸，验收前几乎不可能被发现。

**③ `t_promo` 促销活动表**：`id` / `title` / `content` / `package_id` / `start_time` / `end_time` / `status`

> ⚠️ **「进行中」由两个条件共同决定**（2026-09-30 定稿）：`status = 1` **且** `start_time <= NOW() <= end_time`，**两者打架时以日期为准**。查询条件写作 `WHERE status = 1 AND start_time <= NOW() AND end_time >= NOW()`。
> 理由是 `status` 是一个**手工维护的标记**——活动到期后运营忘了置 0 是运营后台最常见的疏漏；而 `start_time` / `end_time` 是活动自己带的档期，它不会忘。「活动明明写着 8 月底结束，怎么还在首页挂着」是用户一眼就能看出的问题。
>
> ⚠️ `start_time` / `end_time` 为 `YYYY-MM-DD HH:mm:ss` **定宽格式**，前端用**字符串比较**判定档期而非 `new Date()`：`new Date('2026-10-31 23:59:59')` 按**本地时区**解析，带 `T`/`Z` 的 ISO 形式按 **UTC** 解析，两种写法差 8 小时，活动会在最后一天的晚上被显示成「已结束」。定宽格式按位比较的结果与时间先后完全一致。**造数脚本写入这两个字段时必须保持该格式**——写成 `2026/12/31` 或 ISO 形式会让比较得出错误结论，它不报错，只是悄悄判错。

**⑤ `t_order` 套餐办理记录表**：`id` / `user_id` / `package_id` / `order_time` / `status`

> ✅ **生效方式已定稿**（2026-09-30，原待确认问题 25 → 决策「套餐办理即时生效」）：
> - `t_account.package_id` **立即变更**，语义即「即时生效」；
> - `t_order.status` **固定为 `1`（已生效）**，不做状态流转；
> - **本月不另收月费**——当月账单已有一笔月费，不再收第二笔，因此**下单接口不改 `t_account.balance`**。

> 下单接口仍需**只校验、不扣费**地拦两条：套餐已下架（`t_package.status != 1`）拒绝办理；所选套餐与当前套餐相同则拒绝（「无需重复办理」）。

>
> 连带影响大屏「套餐分布」（按 `package_id` 的**当前值**统计，办理后立刻反映）与余量计算（额度取自 `package_id` 指向的套餐，换套餐那一刻余量三个数会跟着跳）。若日后改回「次月生效」，需新增「生效日期」字段 + 定时触发动作，把一处简单写操作变成有状态逻辑——`claude.md` 中记录了当时的权衡。

| `used_data` | decimal(10,2) | 本月已用流量（GB，**与 `t_package.data_quota` 同单位**） |

| `used_sms` | int | 本月已用短信（条） |

唯一键 `uk_user_month (user_id, usage_month)`——**一人一月一行**，从数据库层面堵死"同一月插两行"。

### 5.4 脏数据规则与注入

#### 判脏规则（7 条）

| # | 判脏条件 | 具体表现 |
| --- | --- | --- |
| 1 | 必填字段缺失 | `event_id` / `event_code` / `event_time` / `session_id` / `page` / `region` / `device` 任一为空 |
| 2 | 枚举越界 | `event_code` 不在 12 个之内；`device` 不在 PC / MOBILE / OTHER 之内 |
| 3 | 字段类型错误 | `user_id` 传成字符串；`event_time` 非合法时间格式 |
| 4 | 时间戳非法或越界 | 事件时间落在未来；或早于系统上线日 |
| 5 | 标识格式非法 | `event_id` / `session_id` 不是合法 UUID；`ip` 不是合法 IP |
| 6 | 重复上报 | 同一 `event_id` 出现多次 |
| 7 | 字段超长 / 乱码 | `page` 超 64 字符；含非法编码字符 |

#### 处理方式

统一入 `dwd_behavior_dirty`，**保留原始行 + 失败原因 + 时间 + 来源，不做静默丢弃**。

规则 6 的第一条正常入库，后续重复入死信表（原因 `DUPLICATE`）。识别方式：实时链路用 Redis 记录已处理的 `event_id`（带 TTL），离线链路靠 MySQL 唯一索引冲突。

#### 注入比例（占总量，合计 8.0%）

| 规则 | 比例 |
| --- | --- |
| 必填缺失 | 2.0% |
| 枚举越界 | 1.5% |
| 类型错误 | 1.0% |
| 时间越界 | 1.0% |
| 标识非法 | 1.0% |
| 重复上报 | 1.0% |
| 超长乱码 | 0.5% |

**比例写在配置文件可调，不做界面。** 低于 2% 死信表看不出效果，高于 20% 入库明细失真。

#### 双通道注入

批量脚本**既写 SFTP 文件（走离线），也直接 POST 埋点接口（走实时）**。

> ⚠️ 若只往 SFTP 文件注入，**实时消费服务的清洗逻辑永远跑不到脏数据分支**，那段代码从写完到答辩一次都未被真实触发。而「脏数据过滤」是验收必考环节，拿不出命中记录即为硬伤。

## 8. 数据链路设计

### 8.1 实时链路

```
Playwright 真实浏览器
  → 埋点上报接口（business，只验 JSON 可解析性）
  → Kafka（topic: behavior-log）
  → 实时消费服务（realtime）
      ├─ 洗净判脏 → 合法入 dwd_behavior_log（今天分区）
      │             脏数据入 dwd_behavior_dirty（source=REALTIME）
      ├─ 实时指标 → Redis（供 SSE 推送）
      └─ 计数 → dws_metric_realtime
  → SSE 推送 → 大屏板块①②③（实时部分）
```

### 8.2 离线链路

```
批量造数脚本（读 t_account 真实用户）
  → 生成行为日志文件（含 8% 脏数据）
  → SFTP 上传
  → 拉取至 HDFS
  → Spark 作业（独立 jar，local[*]）
      ├─ 洗净判脏 → 回填 dwd_behavior_log（T-1 及以前）
      │             脏数据入 dwd_behavior_dirty（source=OFFLINE）
      └─ 全量重算 → dws_metric_offline
  → 大屏板块③④
```

> **调度方式待定**（每日定时 / 手动触发），编码时确定。

### 8.3 模拟数据方案

| 用途 | 产生方式 | 说明 |
| --- | --- | --- |
| **历史数据** | 批量造数脚本 | 生成过去 7—30 天的日志文件，走 SFTP 离线链路 |
| **实时数据** | Playwright 驱动真实浏览器 | 跑「浏览套餐 → 登录 → 查话费 → 办套餐 → 报障」真实路径 |
| **脏数据** | 批量脚本注入 | 合计 8%，**双通道**：既写 SFTP 文件，也 POST 埋点接口 |

**为什么必须混合**：
- Playwright 只能产生「此刻」，产生不了「过去」——离线指标必须吃历史数据（7 日留存至少要 7 天前，课设周期内等不出来）。
- 反过来，实时指标要的正是「此刻正在发生」，且这是答辩现场唯一可现场演示的形态。
- 脏数据浏览器点不出来，只能由脚本人为构造。

**脚本必须读真实业务库**：若凭空造用户，大屏「套餐分布」「地域分布」将与 `t_account` 对不上，答辩时一查即穿帮。

## 10. 部署方案

### 服务清单

| 服务 | 镜像 / 形态 | 说明 |
| --- | --- | --- |
| `mysql` | mysql:8 | 业务表 + 行为数据表，共库不同区 |
| `redis` | redis:7 | 缓存 / 在线用户数 / 实时指标 |
| `kafka` | Kafka **KRaft 模式** | 单节点，无 ZooKeeper |
| `sftp` | `atmoz/sftp` | 日志文件上传通道 |
| `hdfs` | NameNode + DataNode | 单机，副本数 1 |
| `spark` | Spark 作业运行容器 | `local[*]`，提交 `offline` jar |
| `business` | Spring Boot | 营业厅 + 管理 + 埋点接口 |
| `realtime` | Spring Boot | Kafka 消费 + 指标 + SSE |
| `frontend` | nginx + 静态资源 | Vue3 构建产物 |

### 硬性约束

> ⚠️ **数据目录（MySQL / Redis / Kafka / HDFS）必须使用 Docker 命名卷（named volume），禁止 bind mount 挂载宿主机目录。**
> 原因是容器内进程 uid 与宿主机目录属主不一致会直接 `Permission denied`，且以「容器启动失败 / 写不进去」的形式出现，排查成本高。

> **代码目录使用 bind mount 无碍**——开发环境已是 Linux 虚拟机，不存在 Windows 与容器之间的文件系统转换。

> **开发环境与部署环境同为 Linux**：开发在 VMware + CentOS 7 虚拟机上，Windows 侧经 **VS Code Remote-SSH** 连接编辑，**不经 Windows ↔ Linux 共享目录（VMware 共享文件夹 / SMB 映射）中转**；compose 文件直接复用于 Linux 服务器，避免环境不一致导致重复踩坑。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **Kafka 起不来 / 消费不消费** | 卡 2—3 天 | 环境阶段优先验证；使用 KRaft 模式去掉 ZooKeeper 一层 |
