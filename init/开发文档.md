## 2. 系统架构

### 2.1 Lambda 架构三层

| 层 | 组成 | 产出 |
| --- | --- | --- |
| **批处理层** | SFTP + 日志文件 + **Flink `OfflineJob`（批模式）** | 全量历史数据 → **准确**的离线指标 |
| **速度层** | Kafka + **Flink `RealtimeJob`（流模式）** | 增量数据 → **实时**指标 |
| **服务层** | MySQL + Redis → Vue3 + ECharts | 大屏与看板 |

> **2026-10-21 架构调整：Spark + HDFS 由 Flink 1.17.2 取代。** 批处理层与速度层现在跑在**同一个引擎**上——两层的差别只是数据源（有界文件 / 无界 Kafka）与运行模式（批 / 流），清洗代码是同一份 `BehaviorValidator`。这不是「多引入一个组件」，而是把原先的两套计算引擎收敛成一套：判脏规则只写一遍，离线对拍与实时清洗不会各漂各的。理由与取舍见 `claude.md` 决策「改用 Flink 替代 Spark + HDFS（批流一体化）」。

### 2.2 两条链路全景

```
造数脚本 ──日志文件──> SFTP ──拉取──> 日志目录 ──> Flink OfflineJob（批）──┐
   │ 读 t_account 真实用户                                                │
   │ 注入 8% 脏数据                                                       ▼
   │                                                  MySQL：明细表(T-1 及以前)
   └──脏数据──> 埋点接口 ──> Kafka ──> Flink RealtimeJob（流）             + 离线指标表
                    ▲                       │
                    │                       ├─> dwd_behavior_log（今天）
              Playwright                    └─> dwd_behavior_dirty（REALTIME）
              (真实浏览器)                          │
                                                    ▼
                                        realtime 服务（只读 MySQL）
                                                    │  每 2 秒查一次
                                                    ▼
                                          SSE 推送 + dws_metric_realtime
                                                    │
                                                    ▼
                                    Vue3 三个标签页（实时 / 离线 / 系统）
```

**两条链路共用一套判脏实现**：`BehaviorValidator` 的七条规则只有一份，离线作业与实时作业各调一次。规则⑥（重复上报）由 `DuplicateChecker` 接口分叉——离线用内存 `Set`，实时用「有界 LRU + 查 `dwd_behavior_log`」。这样改一条规则只改一处，对拍不会出现「离线过了、实时没过」的口径漂移。

### 2.3 指标分工原则（硬约束）

**大屏上每一项指标，只能由实时链路或离线链路其中之一产出，严禁两条链路各算一遍。**

| 链路 | 负责的指标 | 判定依据 |
| --- | --- | --- |
| 实时链路（Kafka → Flink 流） | 在线数、实时 PV/UV、实时趋势曲线、页面热度、行为类型分布、时段热力图 | 可增量累加 |
| 离线链路（Flink 批） | 行为漏斗转化、留存率、地域 / 套餐 / 活跃度分布 | 必须全量重算 |

**理由**：两条链路计算口径必然存在偏差，同一指标双路计算会导致数字对不上，是答辩时最易被追问的破绽。**大屏上每一块图表都必须能回答「这块数据来自哪条链路」。**

## 3. 工程结构

划分为**两个 Web 应用 + 一个计算作业 + 两个支撑模块**：

| 模块 | 形态 | 职责 |
| --- | --- | --- |
| `business` | Spring Boot 应用 | 营业厅接口 + 管理后台接口 + **埋点上报接口** |
| `realtime` | Spring Boot 应用 | **只读 MySQL**：实时指标查询 + SSE 推送；不消费 Kafka |
| `flink-job` | **独立 Flink 作业 jar**（JDK 8） | `OfflineJob`（批）+ `RealtimeJob`（流），共用七条判脏实现 |
| `frontend` | Vue3 工程 | 营业厅 + 分析平台（三个标签页） |
| `mock` | 脚本 | 批量造数（含脏数据注入）+ Playwright 实时流量 |

> ⚠️ **`flink-job` 必须独立成 jar，不得并入 Spring Boot 应用。** Flink 依赖树（Scala 运行时、Akka、Jackson 版本）与 Spring Boot 大面积冲突；且 Flink 作业要提交到集群执行，本来就不该跑在 Web 进程里。

**运行时版本随之一并分层**：`business` / `realtime` 用 **JDK 17**；`flink-job` 用 **JDK 8**（Flink 1.17.2 的官方运行基线）——本地构建用 JDK 17 + `maven.compiler.release=8`，产物在 JDK 8 上跑。**`flink-job` 不继承 `spring-boot-starter-parent`**，否则依赖管理被 Spring Boot BOM 覆盖，绕回依赖地狱。

**为什么业务系统、计算引擎与展示服务三者分开**：Flink 作业是常驻/批处理长任务，Web 接口是请求-响应；**重启业务系统不能连带中断实时消费**，而 Flink 又不能维持浏览器长连接——所以「算」在 Flink，「推」在 Spring。

> **2026-10-21 变更**：原 `offline`（Spark 独立 jar）由 `flink-job` 取代；原 `realtime` 的 Kafka 消费职责迁入 Flink `RealtimeJob`，该服务退为只读 + SSE。

> ✅ **落码状态**（2026-10-21）：上表的**四个模块**均已作为**独立 Maven 工程**落地，互不依赖；三个 Spring 应用各自持有 `Result<T>` 副本（不抽 common 模块——独立构建、独立部署，依赖树必然分叉，共用模块会把三者锁在一起）：
>
> | 工程目录 | 端口 | 职责 | 状态 |
> | --- | --- | --- | --- |
> | `backend/business` | **8082** | 营业厅接口 + 管理后台接口 + 埋点上报 | 营业厅 7 组 15 根 ✅ / 埋点 `POST /api/track` ✅ / **管理后台 `/api/admin/**` 12 根 ✅**（2026-10-21，前端三页已换真请求） |
> | `backend/realtime` | **8081** | 只读 MySQL：实时指标 + SSE 推送 | ✅（Kafka 消费已迁至 `flink-job`） |

## 4. 技术栈

### 4.1 技术要点（对齐 P1 评分清单）

与 P1 技术要点逐项对照，**10 项均有落地方式**（第 3、4 项由 Flink 等价替换，见下方说明）：

| # | 组件 | 采用方式 |
| --- | --- | --- |
| 1 | Kafka 实时接入 | **KRaft 模式，不引入 ZooKeeper** |
| 2 | SFTP 文件传输 | 轻量 SFTP 容器（自建 `alpine + openssh`，sshd 监听 2222；原定 `atmoz/sftp`，2026-10-22 因镜像拉不下来改为自建，见 §10） |
| 3 | HDFS | **由 Flink 直接读日志目录取代**（2026-10-21，见下方说明） |
| 4 | Spark 离线批处理 | **由 Flink 1.17.2 批模式取代**（2026-10-21，见下方说明） |
| 5 | Git | 项目管理 |
| 6 | 单点登录 | **JWT + Redis**，不搭 CAS / OAuth2 |
| 7 | SpringBoot 分层架构 | Controller → Service → Mapper |
| 8 | Redis | 缓存 + 登录 token（**落码口径**：Redis 只承担登录 token 与热点缓存；五个实时指标由 Spring 每 2 秒按 SQL 从 `dwd_behavior_log` 算出并落 `dws_metric_realtime`，见 §7.1 / §8.1） |
| 9 | VUE3 + ECharts | 实时大屏 |
| 10 | Docker 一键部署 | 一套 compose 同时用于开发与部署 |

**明确不采用**：Grafana（面板是配置而非开发）、Filebeat / Logstash（采集方式为埋点直发 Kafka）。

> **Flink 取代 Spark + HDFS（2026-10-21，用户拍板）**
>
> - **为什么**：老师课上只教 Kafka 与 Flink，未教 Spark / HDFS；而本项目需要的是「同一套清洗逻辑跑批与流两种模式」。Flink 一个引擎同时提供批源（文件）与流源（Kafka），**七条判脏规则只写一遍**，避免 Spark Scala 侧与 Java 实时侧各写一份、口径各漂各的。
> - **版本**：Flink **1.17.2**（JDK 8 运行基线，与 `.101` Kafka 3.9.1 同一代际）。
> - **代价如实记录**：P1 技术要点原文的「HDFS」「Spark 离线批处理」两项不再按原字样交付，答辩口径为「Flink 批流一体：同一引擎、同一份清洗实现，分别以有界文件与无界 Kafka 为源」，属技术选型替换而非缺项。
> - **HDFS 的旧定位作废**：原决策「HDFS 排在开发序列最后、是唯一可裁剪项」已无对象——它被「Flink 直接读日志目录」取代，不再是「裁不裁」的问题，而是「不搭了」。

### 4.2 业务功能实现层选型

4.1 的 10 项是「大件」，决定系统由哪些组件构成；本节 7 项是**写业务功能时每天都要用的实现层选型**。两者是上下游关系，不冲突。

| # | 面向 | 选型 | 关键约束（写代码时必须守住） |
| --- | --- | --- | --- |
| ① | 运行时与构建 | 业务侧 **JDK 17 + Spring Boot 3.x**；Flink 作业 **JDK 8 + Flink 1.17.2**（2026-10-21 由「JDK 11 + Spark 3.x」改） | `flink-job` **不得继承 `spring-boot-starter-parent`**；构建用 JDK 17 + `maven.compiler.release=8`；`jakarta.*` 取代 `javax.*`，决定全部依赖坐标 |
| ② | 数据访问层 | **MyBatis-Plus** | 配 `id-type: auto`（默认雪花 ID 与 `AUTO_INCREMENT` 冲突）；`t_account.status` **不用** `@TableLogic`；显式注册分页插件；SB3 下引 `mybatis-plus-spring-boot3-starter` |
| ③ | 认证授权 | **自研拦截器 + JWT + Redis**（开发期白名单用内存 `TokenStore` 替身） | 放行清单须一次定死：登录 / **套餐与活动浏览** / **埋点上报接口** / Swagger 静态资源。漏放行表现为「全站 401」 |
| ④ | 接口文档 | **SpringDoc OpenAPI** | SB3 下坐标为 `springdoc-openapi-starter-webmvc-ui`；`/swagger-ui/**`、`/v3/api-docs/**` 须放行 |
| ⑤ | 前端 | **JavaScript + Element Plus** | 请求集中封装于 `src/api/`；axios 响应拦截器统一解包；**JSON 字段名沿用 `snake_case`，不做 camelCase 转换**；组件库按需引入，**大屏不引组件库**；**须配 `zh-cn` 语言包**——Element Plus 默认 locale 是英文，且按需引入不会连带引入语言包，不配的话分页控件显示 `Total 7`、表格空态显示 `No Data`、日期选择器弹出 `January`（**必须用 `el-config-provider`，不能用 `app.use(ElementPlus, { locale })`——后者会把整个库全量引入，破坏按需引入**） |
| ⑥ | 对象转换 | **手写**（不引 MapStruct） | **脱敏写在这里**（见下） |
| ⑦ | 通用配置 | Lombok / `LocalDateTime` / 埋点分类上报 / `@Cacheable` | 页面浏览类事件走**路由守卫自动上报**，交互动作类**手动调用** |

**配套约定**：统一响应体 `Result<T>`、`@RestControllerAdvice` 全局异常处理、`jakarta.validation` 参数校验。前端 SSE 客户端采用 `@microsoft/fetch-event-source`（原生 `EventSource` 不支持自定义请求头，token 送不出去）。

**认证落码口径**（2026-10-21）：

- **拦截器挂 `/api/**`，放行四项**：`/api/auth/login`、`/api/track`、`/api/packages/**`、`/api/promos/**`。后两项是游客浏览页的数据来源，**只含公开商品信息、不含任何个人字段**；漏放行的表现是首页结构完整、只是套餐与活动两块空着——最容易被当成「数据没造」。
- **401 / 403 由拦截器直接写 JSON**（真实 HTTP 状态码 + `Result` 外壳），不绕 `@RestControllerAdvice`——前端 axios 拦截器按 HTTP 状态码分流，必须在这里定死。
- `@RequireRole` **方法级优先于类级**；`LoginContext`（ThreadLocal）在 `afterCompletion` 清理，否则线程池复用会把上一个用户的身份带给下一个请求。
- **用户身份一律取自 token**，任何接口都不接受前端传 `user_id`。
- ⚠️ **白名单存储本阶段是内存 `TokenStore`**（本地无 Redis），接口与最终 Redis 版一致，上 VM 时只替换 bean。**代价：重启业务服务即全员掉线**，多实例下白名单不共享，内存只增不减（JWT 自带 120 分钟过期，但 store 不主动清理）。见 `claude.md` 决策「认证白名单暂以内存实现代替 Redis」。

**JSON 字段名由全局策略产出**（2026-10-21 落码期简化）：`spring.jackson.property-naming-strategy: SNAKE_CASE` 一处配置，**取代 §5.1「Java 实体用 camelCase + `@JsonProperty` 映射回 `snake_case`」的逐字段写法**。已实测该策略对 Java `record` 同样生效（Jackson 2.19 / Spring Boot 3.5.16），因此实体、DTO、VO **无一处手写 `@JsonProperty`**。新增接口时不必再逐个字段标注。

**统一响应体 `Result<T>`**（2026-09-30 定稿）：全部接口返回同一外壳，**只有 `data` 随接口变化**。

```json
// 成功
{ "code": 200, "message": "操作成功", "data": { } }
// 分页：分页信息放在 data 内部
{ "code": 200, "message": "操作成功", "data": { "total": 12, "pages": 2, "current": 1, "records": [] } }
// 业务失败
{ "code": 1001, "message": "账户余额不足", "data": null }
```

**失败分两层**——判据是「谁该处理」：

| 层 | 管什么 | 取值 | 谁来处理 |
| --- | --- | --- | --- |
| **HTTP 状态码** | 程序层面 | 401 未登录 / 403 无权限 / 500 服务端异常 | axios 拦截器，**写一遍覆盖全部接口** |
| **`code`** | 业务层面 | 200 成功；**1001 起**为业务错误码（不与 HTTP 状态码抢号） | 各页面按需处理 |

登录过期是**二十个接口共同的事**，写一次拦截器全覆盖；「余额不足」是**下单接口独有的事**，写在下单那个页面里。若全塞进 `code`，每个接口都要判一次是不是 401。

**分页口径**（2026-09-30 定稿）：分页类接口**入参**统一为 `page`（从 1 起）+ `size`；**返回**沿用上表 `data` 内的 `{ total, pages, current, records }`，与 MyBatis-Plus 的 `Page<T>` 字段**逐一对应**（后端用的就是它，见选型 ②，字段名无需转换）。营业厅各列表页默认 `size = 5`。

> 前端本阶段用假分页（`src/api/mock/paginate.js`），其返回值**刻意与 `Page<T>` 同形**——接线时只换函数体，页面组件一行不改。假数据形状若与真后端不一致，接线时页面要跟着改，与「把替换成本压到最低」的初衷正好相反。
>
> 入参与返回字段一律沿用全项目命名约定（`snake_case`），**不另创造 `offset` / `limit` / `pageNum` 之类的写法**。

**余量计算落在后端**（2026-09-30 定稿）：余量接口直接返回 `quota` / `used` / `remain` 三个数，**前端不做 `额度 − 已用` 的减法**。理由是这个减法牵着一个**不报错的坑**——`t_package.data_quota` 与 `t_usage.used_data` 单位若不一致（一侧 GB、一侧 MB），相减不抛异常、不报错，**结果只是错**，页面上显示成一个看起来完全正常的数字；而余量在「账户总览」与「余量查询」两处都要用，每多一处自己减一次，这个坑就多一个入口。

**脱敏的实现位置与格式**——由选型 ⑥ 直接推导，是本项目最容易踩的坑：

> 脱敏写在后端 Entity → VO 的手写转换里，**绝不在前端做**。

若后端返回完整手机号、由前端加星号显示，属**假脱敏**：F12 查看接口响应即可见完整号码，Postman 直调接口更是完全绕过，与 P1「最小必要」原则（数据根本不得到达那一层，而非「给了但我不看」）正好相反。正确形态是：接口返回的 JSON 中该字段本身即脱敏态，前端不含任何脱敏代码。

**脱敏格式**（2026-09-30 定稿）：

| 字段 | 格式 | 示例 | 依据 |
| --- | --- | --- | --- |
| `login_name`（手机号） | 前 3 后 4 | `138****1234` | 行业通行，无歧义 |
| `id_card`（身份证） | **前 6 后 4** | `310101********1234` | 18 位结构为 `6 位地区码 + 8 位出生日期 + 3 位顺序码 + 1 位校验码`；**前 6 后 4 恰好整段盖住最敏感的出生日期**，一位不多一位不少，同时保留可认读性 |

> 入库存**明文**，脱敏只发生在出参。用户查看本人信息同样脱敏（见 §6.4 #7）。

**大屏实现约定**（2026-09-30 定稿，适用于 §7 的三个页面）：

| 项 | 约定 | 理由（一句话） |
| --- | --- | --- |
| **适配方式** | 固定逻辑尺寸 **1920×1080** + CSS `transform: scale(k)` 整体缩放，`k = min(视口宽 / 1920, 视口高 / 1080)` | 大屏是固定尺寸的展示场景，宽度已知且固定；scale 是单一全局几何变换，元素**不需要感知缩放** |
| **图表 resize** | `EChart.vue` **刻意不监听 `window.resize`** | 逻辑尺寸恒定 ⇒ 容器 CSS 尺寸永不变；唯一的 resize 监听在 `ScreenLayout.vue`（重算 `k`） |
| **组件库** | 分析平台**零 Element Plus 依赖**——含子页的分页表格、来源筛选、分页器全部自绘 | 深色自绘视觉体系里插一套 `el-table`，要么风格突兀，要么写一堆 `:deep()` 覆盖；**覆盖组件库样式的代码量通常不比自己画一遍少** |
| **页面拆分** | 分析平台为**三个标签页**（2026-10-21）：`/screen/realtime` 实时大屏（板块①② + 24 小时热力图）/ `/screen/offline` 离线数据分析（板块③④，除热力图）/ `/screen/pipeline` 系统运行分析（原样）；`/screen` 保留为 `redirect: '/screen/realtime'`；标签写在布局 `ScreenLayout.vue` 里 | 一屏塞 9 张图 + 5 张数字卡密度过高；拆页依据正是**指标分工**——实时页只放实时链路的图，离线页只放离线链路的图。`/screen` 不直接删：登录落点与旧链接若落空会掉进兜底路由 |
| **埋点** | 分析平台**三条路由均刻意不设 `meta.track`**，访问大屏不产生行为事件 | 分析平台是**观察者**，采集对象是「用户对系统做了什么」（§5.1），给它上报等于让系统观察自己 |
| **轴来源** | 横轴 / 分类轴**由常量清单或日历推导，不得由数据行推导**；缺值落 `null` 或零值，**不改变轴的长度** | 按数据行推轴时，缺值的那一档会被**静默抽掉**而非留空档，图上完全看不出少了 |
| **地图** | geoJSON 必须先 `registerMap()` 完成，**才允许** `setOption`；就绪前 option 为 `null` | ECharts 6 中未注册地图时 `geoSourceManager.load()` 返回 `undefined`，`MapSeries` 直接抛错，**不是画空白图** |
| **路由权限** | **三条**大屏路由（`/screen/realtime`、`/screen/offline`、`/screen/pipeline`）**各自**带 `requiresAuth` + `roles: ['ANALYST', 'ADMIN']`；`/user/*` 带 `roles: ['USER']`；`/admin/*` 三条带 `roles: ['ADMIN']`，布局 `AdminLayout`；「谁能进哪」由 `router/access.js` 的 `isRoleAllowed()` **统一判断**（守卫 / 登录页 `redirect` 校验 / 页头入口显示**四处共用**）；登录页按角色分流（`ANALYST` → `/screen/realtime`，`USER` → 营业厅，`ADMIN` → `/admin/users`）；营业厅页脚的临时入口已删除；大屏头部与管理后台侧栏均带**退出链** | 2026-09-30 定稿并**当日落码**（原为待确认问题 26）；2026-10-21 拆页后**每条路由单独写**，漏一条即出现一个无守卫的大屏页。退出链是加 `requiresAuth` 的**前置条件**——否则 ANALYST 进得去出不来。`/user/*` 不含 `ADMIN`：那是用户自助页，管理员进去看到的是**别人**的余额账单。规则只在路由表 `meta.roles` 写一份，四处调用共用 |
| **管理后台埋点** | `/admin/*` 三条路由**刻意不设 `meta.track`**；`AdminLayout` 的「退出登录」**不调 `reportAction('logout')`** | 与大屏同一条边界，两层理由：① 角色表已定管理员「不产生行为数据」，`tracker.js#send()` 的角色闸会拦掉，写了是死代码；② 即便不拦也不该上报——`dwd_behavior_log` 的分析对象是「**用户**对系统做了什么」，管理员不属于被观察人群 |
| **埋点角色闸** | 分析员与管理员**不产生任何行为事件**——闸落在 `utils/tracker.js` 的 `send()` **唯一出口**，而非各调用点 | 上报入口有三处（路由守卫的页面浏览、`login`、`logout`，将来还有 `order_package` / `submit_ticket`），逐个加判断迟早漏一个。角色表已定两者「不产生行为数据」；`login` 恰是漏斗**第二段**，漏报会让转化率莫名偏高却查不出来 |

> ⚠️ **`null` 绝不 `|| 0` 兜底**：留存 0% 是「一个人都没回来」，`null` 是「还算不出来」，是两句完全不同的话。大屏上刻意留可见缺口（09-30 的 `d1`、近 7 天的 `d7`），断线本身就是事实的可视化。
>
> ⚠️ **ECharts 实为 6.x**（`^6.1.0`），非此前文档所写的 5——版本号**以实查 `package.json` 为准**，理由与「选型① 中小版本在编写 POM 时实查后锁定」相同。
>
> ⚠️ **geoJSON 走 `public/map/china.json` 由浏览器按需 fetch**（582 KB，ECharts 6 仍不内置地图数据），**永不进入 JS bundle**；加载失败**必须 `console.error` 留声**——失败表现为「地域分布一直空着」，与「后端没返数据」长得一模一样。

**② `t_package` 套餐表**：`id` / `name` / `monthly_fee` / `data_quota` / `voice_quota` / `sms_quota` / `description` / `status` / `create_time`

> ⚠️ **三个量纲的单位**（2026-09-30 定稿）：`data_quota` = **GB**、`voice_quota` = **分钟**、`sms_quota` = **条**。`t_usage` 与前端展示**一律沿用同一套**。
> 单位必须全链路统一，因为余量由 `t_package.data_quota − t_usage.used_data` 相减得出——两侧单位若不一致（一侧 GB、一侧 MB），**相减不报错、不抛异常，只是结果错**，页面会显示成一个看起来完全正常的数字。这类错误不崩不炸，验收前几乎不可能被发现。

**③ `t_promo` 促销活动表**：`id` / `title` / `content` / `package_id` / `start_time` / `end_time` / `status`

> ⚠️ **「进行中」由两个条件共同决定**（2026-09-30 定稿）：`status = 1` **且** `start_time <= NOW() <= end_time`，**两者打架时以日期为准**。查询条件写作 `WHERE status = 1 AND start_time <= NOW() AND end_time >= NOW()`。
> 理由是 `status` 是一个**手工维护的标记**——活动到期后运营忘了置 0 是运营后台最常见的疏漏；而 `start_time` / `end_time` 是活动自己带的档期，它不会忘。「活动明明写着 8 月底结束，怎么还在首页挂着」是用户一眼就能看出的问题。
>
> ⚠️ `start_time` / `end_time` 为 `YYYY-MM-DD HH:mm:ss` **定宽格式**，前端用**字符串比较**判定档期而非 `new Date()`：`new Date('2026-10-31 23:59:59')` 按**本地时区**解析，带 `T`/`Z` 的 ISO 形式按 **UTC** 解析，两种写法差 8 小时，活动会在最后一天的晚上被显示成「已结束」。定宽格式按位比较的结果与时间先后完全一致。**造数脚本写入这两个字段时必须保持该格式**——写成 `2026/12/31` 或 ISO 形式会让比较得出错误结论，它不报错，只是悄悄判错。

**⑤ `t_order` 套餐办理记录表**：`id` / `user_id` / `package_id` / `order_time` / `status`

> ✅ **生效方式已定稿**（2026-09-30，原待确认问题 25 → 决策「套餐办理即时生效」）：
> - `t_account.package_id` **立即变更**，语义即「即时生效」；
> - `t_order.status` **固定为 `1`（已生效）**，不做状态流转；
> - **本月不另收月费**——当月账单已有一笔月费，不再收第二笔，因此**下单接口不改 `t_account.balance`**。

> 下单接口仍需**只校验、不扣费**地拦两条：套餐已下架（`t_package.status != 1`）拒绝办理；所选套餐与当前套餐相同则拒绝（「无需重复办理」）。

> ⚠️ **降档时余量会显示为负数并走红色超套样式**——新套餐额度可能低于本月已用量（已用 30 GB 后降到 20 GB 套餐）。**这是刻意的、正确的结果，不是 bug**，前端在降档前弹二次确认说明。
>
> 连带影响大屏「套餐分布」（按 `package_id` 的**当前值**统计，办理后立刻反映）与余量计算（额度取自 `package_id` 指向的套餐，换套餐那一刻余量三个数会跟着跳）。若日后改回「次月生效」，需新增「生效日期」字段 + 定时触发动作，把一处简单写操作变成有状态逻辑——`claude.md` 中记录了当时的权衡。

> **余量 = `t_package` 对应额度 − 本表对应用量**，服务 §6.4 #1（账户总览）与 #4（余量查询）两个页面。
>
> **为什么是汇总式而非流水式**：需求侧没有任何地方要展示"9 月 8 日 19:22 用了 5 分钟通话"这种明细（见 §6.4），而流水式的行数随行为量级膨胀（5 账号 × 12 月 × 每日数十条，造数脚本要写几万行），汇总式仅 **60 行**。大屏若需"每月用量趋势"，汇总式按月一行正好是曲线上的点。
>
> **为什么必须补这张表**：原 6 张表中**没有任何地方存放"已用量"**——`t_account` 只有余额（钱）、`t_package` 只有额度、`t_bill` 是钱不是量。缺口在建「账户总览」页时暴露。用假数据能骗过界面但骗不过后端，故趁后端未动手时补表。

**业务逻辑仅两处**：套餐办理（写 `t_order` + 即时更新 `t_account.package_id`，✅ 口径已定稿见 ⑤）、工单流转（`t_ticket.status` 状态机）。其余功能均为查改。

| --- | --- | --- |
| `id` | bigint PK auto | |
| `event_id` | char(36) | |
| `event_date` | date | **分区列** |
| `event_code` | varchar(32) | |
| `event_time` | datetime(3) | |
| `user_id` | bigint null | 游客为 null |

- **分区**：按 `event_date` RANGE 分区（按月）
- **唯一索引**：`uk_event (event_id, event_date)`

> ⚠️ **MySQL 要求分区列出现在每一个唯一索引中**，因此 `event_date` 必须进 `uk_event`，不能只用 `event_id` 做唯一索引。

**两条链路共写、按时间切分**：实时链路写「今天」，离线链路回填「T-1 及以前」。离线回填用 `INSERT ... ON DUPLICATE KEY UPDATE`，配合 `uk_event` 保证重跑不产生重复行。

> 若只由实时链路写，表里只有当天数据——大屏显示「7 日留存 42%」而成库中最早记录是今天早上，一问即穿帮。按时间切分使两条链路互不重叠，**不违反指标分工原则**（该原则约束的是指标，明细是数据）。

**② `dwd_behavior_dirty` 死信表**：`id` / `source`（`REALTIME` / `OFFLINE`）/ `raw_content` / `fail_reason` / `fail_time`

**③ `dws_metric_realtime` 实时指标表**：`metric_code` / `metric_value` / `stat_time`

**④ `dws_metric_offline` 离线指标表**：`metric_code` / `dimension` / `dimension_value` / `stat_date` / `metric_value`

### 5.4 脏数据规则与注入

#### 判脏规则（7 条）

| # | 判脏条件 | 具体表现 |
| --- | --- | --- |
| 1 | 必填字段缺失 | `event_id` / `event_code` / `event_time` / `session_id` / `page` / `region` / `device` 任一为空 |
| 2 | 枚举越界 | `event_code` 不在 12 个之内；`device` 不在 PC / MOBILE / OTHER 之内 |
| 3 | 字段类型错误 | `user_id` 传成字符串；`event_time` 非合法时间格式 |
| 4 | 时间戳非法或越界 | 事件时间落在未来；或早于系统上线日 |
| 5 | 标识格式非法 | `event_id` / `session_id` 不是合法 UUID；`ip` 不是合法 IP |
| 6 | 重复上报 | 同一 `event_id` 出现多次 |
| 7 | 字段超长 / 乱码 | `page` 超 64 字符；含非法编码字符 |

#### 处理方式

统一入 `dwd_behavior_dirty`，**保留原始行 + 失败原因 + 时间 + 来源，不做静默丢弃**。

规则 6 的第一条正常入库，后续重复入死信表（原因 `DUPLICATE`）。识别方式：**两条链路统一以 MySQL 的 `uk_event(event_id, event_date)` 为准**——离线链路靠唯一索引冲突；实时链路逐条查库（`event_id + event_date`），并发撞键时由唯一索引兜底。原写的「实时链路用 Redis 记录已处理 `event_id`（带 TTL）」**未采用**：TTL 到期后同一 `event_id` 会重新被判为干净，与唯一索引口径漂移，且实时消费要连跑数天，额外维护一份去重集合不划算。

#### 注入比例（占总量，合计 8.0%）

| 规则 | 比例 |
| --- | --- |
| 必填缺失 | 2.0% |
| 枚举越界 | 1.5% |
| 类型错误 | 1.0% |
| 时间越界 | 1.0% |
| 标识非法 | 1.0% |
| 重复上报 | 1.0% |
| 超长乱码 | 0.5% |

**比例写在配置文件可调，不做界面。** 低于 2% 死信表看不出效果，高于 20% 入库明细失真。

#### 双通道注入

批量脚本**既写 SFTP 文件（走离线），也直接 POST 埋点接口（走实时）**。

> ⚠️ 若只往 SFTP 文件注入，**Flink 实时作业的清洗逻辑永远跑不到脏数据分支**，那段代码从写完到答辩一次都未被真实触发。而「脏数据过滤」是验收必考环节，拿不出命中记录即为硬伤。

> - 其余四项：`today_pv` = 今日入库干净事件数；`today_uv` = 今日不同 `session_id`；`today_orders` / `today_tickets` = 对应事件数。四者均为**当日累计、只增不减**，跨零点按新的一天重新数（2026-10-21 起由每 2 秒一次的 SQL 直接从 `dwd_behavior_log` 算出，**不再有内存计数器与「启动时重建」**）。

## 8. 数据链路设计

### 8.1 实时链路

```
前端埋点（tracker.js）
  → 埋点上报接口 POST /api/track（business，只验 JSON 可解析性）
  → Kafka（topic: behavior-log，3 分区，跑在 192.168.23.101）
  → Flink RealtimeJob（group=behavior-realtime-flink，并行度 1）
      ├─ 洗净判脏（BehaviorValidator + DbDuplicateChecker）
      ├─ 合法 → dwd_behavior_log（今天分区）
      └─ 脏数据 → dwd_behavior_dirty（source=REALTIME）
  → realtime 服务（8081，只读 MySQL）
      ├─ 每 2 秒按 SQL 算五个指标 → upsert dws_metric_realtime
      └─ SSE 推送 GET /api/realtime/metrics（一条消息一个指标）
  → 大屏实时页（板块①② + 热力图）
```

> **落码状态（2026-10-21，本地打通）**：`business`（8082）、`realtime`（8081）、`flink-job` 三个独立 Maven 工程，`analysis-service`（8080）不变。
>
> - **洗净已迁入 Flink**：七条规则由 `etl/etl.py` 逐条移植到 `BehaviorValidator`（顺序 / 正则 / 边界一致），离线与实时共用同一份实现。规则⑥（重复上报）通过 `DuplicateChecker` 接口分叉——实时侧 `DbDuplicateChecker` 用「上限 10 万条的 LRU + 查 `dwd_behavior_log(event_id, event_date)`」；长跑作业不能像离线那样把 `Set` 无限撑大。
> - **指标不再常驻内存**：`MetricService` 每 2 秒直接从 `dwd_behavior_log` 按 SQL 算五个指标。这样 Flink 作业重启、Spring 服务重启、跨零点，都不需要「从库重建累计量」这段易错逻辑——库本身就是唯一真相。代价是每 2 秒一次聚合查询，演示规模下可忽略。
> - **实时指标不落 Redis**：Redis 只承担登录 token（决策「单点登录 JWT + Redis」），本链路不依赖它是否在线。本机开发期 token 白名单由 `business` 的内存 `TokenStore` 替身承担（上 VM 换 Redis，见 §4.2「认证落码口径」）。
> - **实时落库批量 = 1**：`DwdSink` / `DirtySink` 在实时作业里一条一提交，保持与原 `ack-mode=record` 相同的可见性，避免「数据到了但大屏要等一批」。
> - **时区红线**：`event_time` 存的是 **UTC 字面量**，JDBC 必须用 `setObject(LocalDateTime)`；`Timestamp.valueOf()` 会按 JVM 默认时区再换算一次，在 UTC 的 Linux 上整体偏 8 小时，**不报错、只是时间全错**。
> - **验收**：七条规则各命中一次、干净行入库一次、重复上报只进死信、SSE 每 2 秒 5 条、重启后累计量不变、离线对拍仍为 56,220 / 4,889 / 62。口径见 `claude.md` 决策「实时消费迁入 Flink，Spring realtime 退为只读 + SSE」「Flink 两条作业落码口径与验收结果」。

### 8.2 离线链路

```
批量造数脚本（读 t_account 真实用户）
  → 生成行为日志文件（含 8% 脏数据）
  → SFTP 上传
  → 拉取至日志目录（开发期直接读本地 mock/out）
  → Flink OfflineJob（独立 jar，有界文件源）
      ├─ 洗净判脏 → 回填 dwd_behavior_log（T-1 及以前）
      │             脏数据入 dwd_behavior_dirty（source=OFFLINE）
      └─ 全量重算 → dws_metric_offline
  → 大屏离线页（板块③④）
```

> **调度方式待定**（每日定时 / 手动触发），编码时确定。

> **落码状态（2026-10-21）**：`backend/flink-job` 的 `OfflineJob` 已与 `etl/etl.py` 逐项对拍通过——同一份 `mock/out/` 输入，两边都得到 **入库 56,220 / 判脏 4,889（8.00%）/ 离线指标 62 行**，漏斗 **20,551 → 3,654 → 3,037 → 638**，`event_time` 范围一致。`etl/etl.py` 保留为不依赖 JVM 的对照实现。
>
> **SFTP 段已打通（2026-10-22）**：`.101` 造数 → `sftp` 上传到 `.102:/root/demo01/in`（15 个文件 / 18 MB）→ 提交到 `.102` 集群的 `OfflineJob` 读取该目录，45.9 秒 FINISHED，结果仍是 **56,220 / 4,889 / 62**。当天晚些时候容器化部署落地，SFTP 对端可用自建容器（`deploy/sftp`，`demo01@192.168.23.133:2222`，上传卷 `/home/demo01/upload`）——已验证上传成功；`OfflineJob --input` 若要改读该卷，走的是「挂载 / 同步到 `.102`」这一步，本轮未改。HDFS 仍不实施。
>
> ⚠️ **造数脚本的「未来时间」有保质期**（2026-10-22 撞上并修复）：`TIME_OUT_OF_RANGE` 脏行早先按 `now + 1~30 天` 注入，真实时间追上来后这些行会变成干净行、却仍躺在旧日期的文件里，批作业因「文件日与 `event_date` 不符」直接失败。现改为 `now + 365~3650 天`，永久判脏。**验收前若要重新造数，务必带 `--end 2026-10-19`**（默认「昨天」会让文件窗口漂移）。
>
> ⚠️ `OfflineJob --reset` 会 `TRUNCATE` 整张 `dwd_behavior_dirty`（含 `REALTIME` 行）——**跑离线重置前先停实时作业**，否则实时死信会被一并清掉。这是与 `etl.py` 同源的既有行为，不是新缺陷。

### 8.3 模拟数据方案

| 用途 | 产生方式 | 说明 |
| --- | --- | --- |
| **历史数据** | 批量造数脚本 | 当前生成 **2026-10-06 ~ 10-19 共 14 天**、500 个用户的日志文件，走离线通道 |
| **实时数据** | Playwright 驱动真实浏览器 | 跑「浏览套餐 → 登录 → 查话费 → 办套餐 → 报障」真实路径 |
| **脏数据** | 批量脚本注入 | 合计 8%，**双通道**：既写日志文件，也 POST 埋点接口；本地最小闭环只走文件通道 |

**当前数据规模**（2026-10-20，`mock/out/`）：采集 **61,109 行** = 入库 **56,220**（登录用户 19,236 + 游客 36,984）+ 判脏 **4,889（8.00%）**；入库明细含 **22,644 个会话**；漏斗 **20,551 → 3,654 → 3,037 → 638**。登录用户按 HIGH / MID / LOW 三档活跃度生成（回访概率不同，条数因此不同），游客会话 20,000 个、5% 转登录。

**为什么必须混合**：
- Playwright 只能产生「此刻」，产生不了「过去」——离线指标必须吃历史数据（7 日留存至少要 7 天前，课设周期内等不出来）。
- 反过来，实时指标要的正是「此刻正在发生」，且这是答辩现场唯一可现场演示的形态。
- 脏数据浏览器点不出来，只能由脚本人为构造。

**脚本必须与业务库一致**：若凭空造用户，大屏「套餐分布」「地域分布」将与 `t_account` 对不上，答辩时一查即穿帮。正式链路由脚本读 `t_account`；本地最小闭环由 `etl/etl.py` 读 `users.json` 灌入 `t_account`，二者同源，分布仍对得上。

## 10. 部署方案

### 服务清单

| 服务 | 镜像 / 形态 | 说明 |
| --- | --- | --- |
| `mysql` | mysql:8 | 业务表 + 行为数据表，共库不同区 |
| `redis` | redis:7 | 缓存 / 在线用户数 / 实时指标 |
| `kafka` | Kafka **KRaft 模式** | 单节点，无 ZooKeeper |
| `sftp` | 自建 `alpine:3.20 + openssh`（`deploy/sftp`） | 日志文件上传通道，sshd 监听 2222。原定 `atmoz/sftp`，本机镜像站只代理 `library/` 拉不下来，2026-10-22 改为自建 |
| `flink` | Flink **1.17.2** 集群 | 提交 `flink-job` jar：`OfflineJob` 批、`RealtimeJob` 流；`-Pcluster` 构建（Flink 核心置 `provided`，约 20 MB） |
| `business` | Spring Boot | 营业厅 + 管理 + 埋点接口 |
| `realtime` | Spring Boot | 只读 MySQL + 指标 + SSE（不消费 Kafka） |
| `frontend` | nginx + 静态资源 | Vue3 构建产物 |

> **容器化部署已落地（2026-10-22）**：编排文件为仓库内 `deploy/docker-compose.yml`（七个服务：mysql / redis / sftp / business / realtime / analysis / web），部署目录 `192.168.23.133:/opt/demo01`。**全部用 host 网络**——`.133` 的 docker 网桥下宿主机与容器双向不通（容器互访反而正常），端口即宿主端口、容器间地址写 `127.0.0.1`；原因与实测过程见决策「应用层容器化部署落地（host 网络 + 七容器）」。三个 Spring 服务共用一个镜像 `demo01-app:0.1.0`，靠 `command` 选 jar。数据库由 `mysqldump` 打进 `/docker-entrypoint-initdb.d` 随首次启动导入。

> **开发期实际拓扑（2026-10-21，2026-10-22 更新）**：Kafka 3.9.1 在 `192.168.23.101`；Flink 1.17.2 装在 `192.168.23.102`（本机另用 JDK 8 跑本地 Flink 做联调）；MySQL 原先在**开发者的 Windows 主机**（VMnet8 网关 `192.168.23.1:3306`）——那时 `.102` 上的作业要连它，必须同时满足三件事：① 建允许远程的来源账号；② Windows 防火墙放行 3306；③ 作业参数写 `--host 192.168.23.1`。三项缺一，报错都是「连接超时」，看不出是哪一项。
>
> **2026-10-22 起，实时作业的库改为 `.133` 的容器 MySQL**（`--host 192.168.23.133 --user demo01 --password 123456`，host 网络下 3306 直接开在宿主机上），上面三件事随之只对**离线作业的旧写法**有效；开发机 MySQL 仍是本地联调与 `mysqldump` 的数据源，但不再接收实时写入。

### 硬性约束

> ⚠️ **数据目录（MySQL / Redis / Kafka / Flink checkpoint）必须使用 Docker 命名卷（named volume），禁止 bind mount 挂载宿主机目录。**
> 原因是容器内进程 uid 与宿主机目录属主不一致会直接 `Permission denied`，且以「容器启动失败 / 写不进去」的形式出现，排查成本高。

> **代码目录使用 bind mount 无碍**——开发环境已是 Linux 虚拟机，不存在 Windows 与容器之间的文件系统转换。

> **开发环境与部署环境同为 Linux**：开发在 VMware + CentOS 7 虚拟机上，Windows 侧经 **VS Code Remote-SSH** 连接编辑，**不经 Windows ↔ Linux 共享目录（VMware 共享文件夹 / SMB 映射）中转**；compose 文件直接复用于 Linux 服务器，避免环境不一致导致重复踩坑。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **Kafka 起不来 / 消费不消费** | 卡 2—3 天 | 环境阶段优先验证；使用 KRaft 模式去掉 ZooKeeper 一层 |
| **Flink 作业提交失败 / 版本不匹配** | 卡 1—3 天 | 版本锁死 **1.17.2 + JDK 8**；集群包用 `-Pcluster` 构建（Flink 核心 `provided`），本地联调用 fat jar，两种包不可混用 |
| **JDBC 时区偏移** | 时间全错但不报错 | 一律 `setObject(LocalDateTime)`，禁用 `Timestamp.valueOf()`；对拍 `event_time` 范围 |
| **实时作业长跑内存 / 去重集合膨胀** | 作业 OOM 或误判重复 | 规则⑥用「上限 10 万条 LRU + 查 `dwd_behavior_log`」；并行度固定 1，不跨分区共享状态 |
| **`.102` 连不上 MySQL** | 作业起来了但一条也写不进 | 远程账号 + 防火墙放行 + `--host` 三项一起验；先用 `nc -vz <host> 3306` 确认端口。**实时作业现连 `.133`**（账号 `demo01`，只授 `demo01.*`）；**离线作业仍是开发机 `192.168.23.1`** 的旧写法 |
| **集群包误用 fat jar** | `NoSuchMethodError` / 类冲突 | 集群提交只认 `-Pcluster` 产物；提交时显式 `-c com.demo01.flink.RealtimeJob`（Main-Class 是 `OfflineJob`） |
| **两人同时算同一指标** | 答辩时数字对不上 | 严格遵守「指标分工原则」，每块图表标注链路归属 |
| **离线数据与业务库对不上** | 答辩时一查即穿帮 | 造数脚本必须读 `t_account` 真实用户 |
| **实时链路清洗逻辑从未被触发** | 验收必考环节无证据 | 脏数据双通道注入，保证 `source` 两种取值均有数据 |
| **5 人并行接口对不齐** | 返工 | 按模块分工（业务 / 实时 / 离线 / 前端 / 造数与测试），减少交叉 |

**体量参考**：按 5 人小组、课设周期、无智能体辅助的口径估算，全项目约 **88—120 人天**，5 人分摊每人 **18—24 人天**。8 周周期下仅「刚好打平」，**无返工与排错余量**——这是「不扩量、留缓冲」决策的直接依据。
